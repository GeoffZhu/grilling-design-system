# Design translation rules

## UI images

Separate observed properties from inferred ones. Record palette roles, type proportions, border treatment, spacing rhythm, icon geometry and special component patterns. Preserve the recognizable composition and style when adapting Mobile UI to PC. Do not render the device frame as a product component. Extend the language to controls, menus, tables and overlays.

Implement image-specific components from the current input analysis; the generic starter is only scaffolding. Never reuse another session's subject matter or ornamental treatments as defaults.

## Non-UI images

Map material/light to surface and elevation, color relationships to semantic roles, dominant geometry to shape, visual rhythm to density, and subject character to typography/icons. State which qualities are translated. Offer two component treatments only when a planned high-impact decision needs them; otherwise derive one. Explain visible differences in everyday words. Avoid using the entire photo as a background to imitate its atmosphere.

## Foundation choices

- Color: foreground/background pairs, primary action, secondary, accent, muted, destructive, focus, charts and sidebar.
- Typography: rendered heading/body fonts, hierarchy, weight, line height, numeric/text specimens, CJK fallback when needed.
- Spacing: control height, rhythm, internal padding, component gaps and touch targets.
- Shape: radius scale, border contrast/width, elevation and selected-state treatment.
- Icons: show comparable action icons (add, search, back, check, settings) with explicit family, size, stroke, corner and fill decisions. Bound icons inside Buttons to the icon token and apply smaller optical caps to compact buttons. Keep decorative characters separate.
- Motion: show real hover/press/open behavior, durations and easing; respect reduced motion.

Tokens alone cannot implement every style. Extend CSS and component variants when required; keep extensions in a dedicated theme file and include it in registry distribution. When changing template CSS, verify it reflects the accepted values in both preview and final library.

Derive a theme signature matrix from the Key Visual and representative custom components before styling the complete library. For actions, inputs, selection, navigation, data display, overlays, and feedback, record the intended depth, semantic color role, and visible interaction state. Apply that matrix to representative official components without changing their APIs. Preserve hierarchy: strong actions and elevated overlays may inherit solid depth; dense Item rows and secondary utilities should remain lightweight.

Apply frontend-craft.md for the design-intent and screenshot critique passes. Prefer a specific hierarchy of type weights, geometry and surface roles over globally applying one large radius and heavy weight. Every visible label, separator, illustration and motion should have a purpose in the image-derived design. The reference wins when it intentionally uses a familiar style.

## Responsive and accessibility

Use component specimens or relevant sections for preference decisions, with enough room to compare at readable sizes. Use full 16:9 Desktop and 9:16 Mobile frames side by side for the sole integrated presentation. Preserve zoom gestures and scrolling without zoom controls or hints. Separately use 1440×900 as the PC target and 390/360 px for Mobile checks. Keep primary touch targets at least 44 px and do not shrink type to force fit. Use actual focusable controls, labels, descriptions, and keyboard behavior. Apply antialiased font smoothing in every preview document.

Calendar is a density canary: keep its default cell size at least 40px and no smaller than the system's normal control height. Month/year dropdown captions are full controls with at least a 40px hit area, stable locale-safe widths, balanced inline padding, and a bounded disclosure glyph. A custom day with secondary text is not a default square day: give it a taller non-square row, explicit vertical padding and a small internal gap so both lines fit without collision. Single selections and range endpoints retain an explicit semantic fill after Button variant rules; focus follows the cell radius rather than drawing an oversized circular halo. At narrow widths, preserve the cell and type size, reduce only surrounding preview padding, and give multi-month variants their own local horizontal scroll or responsive month count. Card footer is an alignment canary: use equal top and bottom padding, align-items center, and enough minimum height for the normal control plus its intended inset. Verify default, small, wrapped, full-width-button, and icon/text footer content.

For portal overlays, define an explicit stack: backdrop above persistent application/gallery chrome, content one layer above the backdrop. Sheet content also needs fixed positioning and side geometry; source order alone is not a stacking contract. For Base UI Switch, target the root's reflected `data-checked` and `data-unchecked` attributes and move the descendant thumb from those root states; do not assume Radix-style `data-state` on the thumb. For Input Group, the wrapper alone owns border, radius, background, shadow, focus ring, and descendant clipping. Use `overflow:hidden` on that wrapper so filled addons and buttons cannot cover its rounded border; wrapper-owned outer shadows remain visible. Reset the direct input/textarea border, background, shadow, and inner focus treatment after all theme signature rules.

Within Input Group, inline-start/inline-end addons and buttons use sufficient padding and exactly one separator from the editable region. Block-start/block-end addons make the wrapper wrap, occupy a full-width row, and use one top/bottom boundary; textarea is a separate full-width row with a stable minimum height and internal padding. Multiple inline addons may meet without creating double separators.

Checkbox uses a compact painted box plus an independent pseudo-element touch target. Give the painted root an explicit inline-grid box, zero padding and line-height, make the indicator cover that box with absolute inset centering, and size the SVG explicitly. Exclude Checkbox from generic coarse-pointer minimum dimensions so the hit target grows without moving the visual center.

Use the actual primitive state contract for composite navigation. Base UI Navigation Menu exposes data-popup-open on its trigger, while Tabs exposes truthy data-active; style the open/active state without requiring a literal true value. Default active Tabs use accent/accent-foreground and may add border/shadow without changing layout; inactive Tabs clear background, border, and shadow. A line Tabs list and all its triggers have no border or shadow. Its active trigger remains transparent and uses only an indicator inset from both ends by at least 8px or half the control radius, whichever is larger. The indicator cannot overlap a rounded trigger region. Keep hover from replacing the Navigation Menu's open treatment. Links inside Navigation Menu content must use block-level, full-width boxes so hover/focus backgrounds paint one continuous region; muted descendants then use the accent foreground. For a SidebarMenuButton that opens a portaled DropdownMenu, style its data-popup-open state with sidebar semantic colors and remove border, background, and shadow from its nested Item. Because the popup leaves the sidebar ancestry, add an explicit context class to the generated sidebar example's DropdownMenuContent and a stable positioner hook; use those hooks for anchor width, viewport bounds, and a layer above sticky documentation chrome. Keep a deliberate vertical gap between the sidebar's account/version switcher and search control, and review their alignment, padding, and density together at Desktop and Mobile sizes.

For Collapsible, bind open styling to Base UI's truthy `data-panel-open` on the trigger. Pair the hover/focus/open background and foreground, and carry that foreground into SVG icons, `[data-icon]`, and muted descendants. The disclosure icon rotates from `data-panel-open`; a familiar-looking `data-state=open` selector is not a substitute for the emitted DOM contract.

Define explicit internal grids for compound feedback and overlays. Command Input has one separator at its wrapper and a borderless full-width search row. Its internal Input Group is exempt from generic addon separators and padding; the row owns stable inline padding and gap. Command group headings have a deliberate bottom inset before a vertically gapped item collection, and items own a readable minimum height, balanced padding, and bounded 16px leading icons. Navigation Menu and Select chevrons use a 16px inline-flex wrapper with zero line-height and a separately bounded 16px glyph, so intrinsic SVG geometry or broad descendant selectors cannot upset optical centering. Dialog close is a bounded icon action pinned to a top corner with enough title clearance. Alert reserves a leading column for a direct icon or alert-leading slot and a separate trailing action column. Avatar default/sm/lg roots have explicit square dimensions. Message Scroller content owns vertical message spacing instead of relying on Bubble margins.

Button Group is one frame, not a row of standalone controls. Put border, radius, clipping, background, and elevation on the outer group. The elevation must use the theme shadow token and reference-derived hierarchy, including `none` in a flat design; never substitute a fixed extruded shadow. Reset direct Button, Input, Select/Dropdown trigger, Input Group, text, and nested-group frames, then draw one separator between adjacent children according to orientation. Explicit separator components replace the automatic separator at that position. Use inset focus outlines and suppress standalone pressed translation/shadow so focus and activation never change layout or create double borders.

Card forms keep consistent FieldGroup, Field, and footer action gaps. Invalid states use a destructive boundary and restrained 2px translucent ring without changing layout. A compound Input Group renders invalid treatment only on its wrapper; direct controls clear their own ring. Error text follows its control closely with a small fixed gap.

Use AA contrast targets: 4.5:1 normal text, 3:1 large text and essential UI boundaries/focus. Fix low-contrast source details with a visible explanation during choice. Token reports are partial evidence, never blanket WCAG certification. Preserve familiar disabled affordances while ensuring context is clear. Avoid color-only status. Chart palettes also need labels/patterns.

Use meaningful custom APIs with controlled/uncontrolled state where useful. Do not bake example content into the component library. Group files under `components/custom/` as "Custom components" in galleries, and give every component its own specific name and detail page. Stickers may be original SVG/CSS approximations; identify them as interpretations, not extracted originals. Bundle required assets and licenses or state intentional limitations.
