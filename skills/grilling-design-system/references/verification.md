# Verification and delivery evidence

## Available capabilities

Follow host browser instructions: default to agent-browser for local development validation and playwriter for other browser tasks when available. Use actual tool schemas. No named browser package, CLI, extension, or installation is a prerequisite. Do not install a browser tool just to satisfy this skill. Use existing capabilities when present; otherwise inspect source, run build and contrast checks, serve HTML for the user, and record the missing visual or interaction checks explicitly.

Keep known defects separate from unavailable verification. Fix defects before showing the result. Use visualReview.method: source-inspection with nonempty limitations when screenshot inspection is unavailable. Never use a placeholder image as review evidence or label unexecuted checks as passed. Placeholder imagery inside the reviewed UI must follow the policy in SKILL.md and be replaced before production. Carry limitations into DESIGN.md and the delivery response.

Apply the checks below only to components in the recorded inventory; do not add admin components to a marketing site for validation. For optimization, inspect actual target pages and affected shared consumers as well as the gallery.

## Per preview

1. Run the target-framework build through studio.js verify using the host command in Web projects and standalone command otherwise; provide explicit output paths and retain buildId. See protocol.md. For a session-hosted build, run `studio.js snapshot` into a new candidate name and publish only its returned path; do not manually copy or overwrite a preview directory. Inspect focused HTML specimens for earlier decisions.
2. Serve locally. When browser capabilities exist, inspect the specimen at its declared viewport and the integrated page at 1440 by 900, 390 by 844, and 360 by 800.
3. Check Mobile overflow, readable text, and touch targets. When device emulation exists, verify coarse-pointer behavior, Switch on/off and default/small sizes, thumb insets, and the independent hit area.
   Confirm Base UI Switch root state attributes drive both the painted track and descendant thumb; checked and unchecked must differ visibly without relying on a thumb `data-state` attribute.
   For checked Checkbox, read computed styles and bounding rectangles for the root, indicator, and SVG. The root remains the documented painted size, indicator bounds match the root, and the SVG center matches the root center within one CSS pixel. Confirm its pseudo-element supplies the larger coarse-pointer hit area.
4. Scan every component detail page at Desktop and Mobile. Assert each `.visual-example-canvas` has no horizontal overflow and every example stays within it. Check bounds against the actual canvas and example-content rectangles. Wide tables, navigation groups, and composite controls may scroll only inside their owning component container. Verify the container-responsive one-column fallback; browser viewport width alone is not evidence.
5. Inspect Calendar at 100% zoom inside the real documentation canvas. Confirm default day cells are at least 40px and no smaller than the normal control height; multi-month variants may scroll only inside their own example. For dropdown captions, measure at least 40px height, locale-safe month/year widths, balanced padding, and bounded chevrons. For custom days with secondary text, verify a taller non-square row, both lines inside the cell, a small gap, and no overlap with adjacent rows. Confirm single selection and range endpoints retain an opaque semantic fill after Button styles, while keyboard focus follows the cell shape without an oversized circle. Inspect Card footers with default, small, wrapped, full-width-button, and icon/text content. Confirm controls are vertically centered and top/bottom padding is balanced.
6. Operate representative controls, a form, a custom component, and an overlay. Check keyboard focus, close/return focus, invalid states, and reduced motion where supported.
   For every included Select implementation, open the actual option popup on Desktop and Mobile. Inspect its surface, text, border, radius, padding, option height, selected indicator, hover/focus, and disabled states against the theme; include an opened-popup screenshot in component visualReview when capture is available. A closed-field screenshot, styled chevron, or DOM value assignment does not verify the popup. Check long labels, scrolling, trigger/content width, viewport-edge collision, and layering in a card and any supported overlay container. Apply this opened-state check to other included menus, comboboxes, popovers, and date pickers. An unintended browser/OS picker is an implementation defect, not a browser-verification limitation; repair it unless a native exception is documented under design-rules.md.
   Select an option through real pointer and keyboard actions. Test Enter/Space, arrows, Home/End and typeahead where supported, skipping disabled options, Escape cancellation, outside dismissal, and focus return. Confirm one selection updates the value once and leaves the popup closed; Enter must not reopen it after focus returns. Exercise controlled and uncontrolled examples. For form-capable APIs, test required/error association, name/form submission with no duplicate field, and reset of both the visible label and submitted value. A hidden form bridge must remain outside the tab order and route invalid focus to the visible control. Document exact unsupported checks instead of substituting programmatic value changes for keyboard evidence.
   Open every Sheet side over the sticky gallery header and Mobile navigation. Confirm the backdrop covers all chrome and the Sheet content remains one stack level above it. Inspect Input Group with inline-start/end addons and buttons: require one outer frame, wrapper overflow hidden, child fills clipped inside both rounded corners, adequate addon padding, one internal separator, and no nested button shadow. Confirm the wrapper's own focus/invalid outer shadow remains visible. Inspect block-start/end addons with textarea: each occupies a full-width row with one boundary and textarea keeps its minimum height. For invalid Input Group, wrapper alone carries a destructive border and subtle 2px ring; nested controls have no repeated ring and error text is adjacent.
   Inspect Command search for one bottom boundary and an unconstrained input. Confirm generic Input Group addon padding/separators do not apply inside Command. Measure the search row's inline padding/gap, group-heading bottom inset, gap between item rows, item minimum height/padding, and 16px leading icons; test both short and long labels with shortcuts. Open Navigation Menu and Select and measure each disclosure wrapper and glyph at 16×16px; each wrapper uses inline-flex, zero line-height, and align-self center, and broad SVG rules do not change the glyph. Move the pointer between Navigation Menu's trigger and content, and confirm the open trigger does not fall back to the hover treatment. Content links must compute to display block and width 100%, paint one continuous hover background across their row, and use the accent foreground for muted descendants. Switch Tabs and verify only the truthy data-active trigger is selected. Default active Tabs must compute to accent/accent-foreground with a visible border or shadow; inactive Tabs must clear those treatments. For line Tabs, confirm the list and every trigger compute to no border and no shadow, then measure the selected indicator: it remains transparent apart from the indicator and is inset from both trigger ends by at least 8px or half the control radius, so it never enters a rounded area. Open the SidebarMenuButton DropdownMenu and verify the trigger uses sidebar open colors, its nested Item has no border/background/shadow, and the portaled popup plus positioner use anchor width and a layer above gallery chrome. Inspect the sidebar header at Desktop and in the Mobile drawer; its account/version switcher and search region need a visible vertical gap, aligned edges, and no overlap or crowding. Open Dialog and confirm its close icon is aligned, interactive, and clear of the title. Check Alert with no icon, direct icon, explicit leading slot, description, and trailing action. Measure Avatar sm/default/lg bounds and verify gallery wrappers do not stretch them. Scroll messages and confirm a stable gap between every adjacent Message Scroller item.
   Inspect Collapsible folder rows in closed, hover, focus-visible, and open states. Confirm the trigger uses Base UI `data-panel-open`, background and foreground remain a contrast pair, all text/SVG/muted descendants use the intended foreground, and the disclosure icon rotates without changing layout.
   Inspect Button Group with Button, Input, Select, Dropdown, text, Input Group, nested groups, and explicit separators in horizontal and vertical orientations. Computed styles must show the outer group as the only border/radius/shadow frame, child outer borders and shadows as none, and exactly one 1px separator per adjacency. Its computed shadow must equal the theme shadow token; if that token is `none`, the group must remain flat. Focus and pressed states must not alter element bounds or add a second outline. Inspect the Input OTP form's Resend Code button and measure its SVG: it must use the compact optical size, preserve its aspect ratio, and remain visually subordinate to the text.
   Inspect Input Group In Card, including Feedback & Comments. Measure FieldGroup gap, per-field label/control gap, textarea and block addon separation, footer action gap, and spacing to nearby fields. Compare standalone Input, Textarea, Select and grouped invalid states; none may render a thick red halo or shift layout.
7. Trigger every global feedback API represented in the gallery. For Sonner, click a `toast()` example and verify that a rendered toast appears in the accessibility tree and viewport; source inspection of the click handler alone is insufficient. Confirm each singleton host or provider is mounted once at the application root.
8. Read contrast-report.json and inspect actual foreground/background combinations in source. Fix failures; semantic reports alone do not cover all rendered combinations.
9. Inspect the overview at Desktop and Mobile. The confirmed integrated Key Visual must be the first substantive section after its heading, before the complete component directory, and must render the delivered components. A separate session presentation does not satisfy this gallery check. Confirm the docs-only composition is absent from componentEntries, custom-components.json, component counts, registry.json, public/r/all.json, package exports, and consumer copy guidance.
10. When screenshots are available, view them at actual size, including relevant component crops and states. Compare the original image, the reference-derived fragment, and representative Button, Input, Checkbox, Tabs, Dialog, Table, Alert, and Toast using visual-translation.md. Apply visual-analysis.md's hierarchy, silhouette, distribution, anatomy, asset, and transfer checks. Confirm shared rules and intentional role-specific differences without making every family equally saturated or elevated. Check that prominent reference traits survived outside the Key Visual and after full generation. Review type hierarchy, spacing, shape, icons, states, composition, and copy; repair issues and recapture. See frontend-craft.md.
11. Save visualReview per component candidate and integrated presentation with the accepted token hash, real observations, and no known unresolved defects. Record limitations separately. Preview checks must describe actual results or explicitly identify checks not run. Before publishing, confirm snapshot creation validated the entry JS plus static/dynamic chunk closure; `studio.js publish` must reject missing or changed assets.

## Workflow validation

Use temporary --simulation sessions for explicitly requested simulated runs. Record simulated responses through studio.js decide; never add decision controls to HTML or edit session state to skip a pending response. Keep simulation status visible in state and DESIGN.md.

Cover a planned visual choice, the real available single-select tool when a human participates, a derived checkpoint, one integrated presentation, revision feedback, updated foundations/components, explicit confirmation, and source/applicable registry/DESIGN.md delivery and real updated pages for optimization. Automated tests can submit simulated protocol responses but cannot claim they tested a real question popup. Check resume and retained history. Ensure feedback causes a visible change.

## Final delivery

- New SaaS: fetch all registry:ui items from one snapshot. Existing SaaS: cover target pages and related components with the host library. Marketing: cover nine custom families; SaaS homepages add nine marketing-* families. Verify source attribution and inventory against the chosen branch.
- Verify the requested output directory takes priority. In Web projects put the module there or under the actual source root/design-system, and DESIGN.md at the application root. Outside Web projects put the complete app and DESIGN.md at the selected app root.
- Include components, gallery, tokens, native styles, snapshot, licenses, and DESIGN_DOC. Web integration reuses the host manifest/lockfile and includes a compatible registry where supported. Standalone delivery includes its own manifest/lockfile and applicable registry; marketing uses a source snapshot without a registry. Both components and DESIGN_DOC are mandatory.
- Run the final build through studio.js verify and include buildId in delivery evidence. Build, source or artifact changes invalidate the receipt. Where browser access exists, inspect lazy gallery rendering, runtime errors, and visual consistency across forms, navigation, overlays, charts, and feedback components.
- In Web projects verify host build/typecheck/lint, imports, framework boundaries, formatting, aliases, and dependencies. Test any registry in a consumer matching that stack. For standalone SaaS delivery, serve LIBRARY/public and install r/all.json into a clean React + Tailwind 4 consumer, then build and check theme imports.
- For marketing, copy the snapshot file closure and dependencies into a clean compatible consumer and build it; verify no shadcn imports or dependencies. For a registry, verify source imports, dependency versions, theme files and required assets/fonts.
- Verify custom theme rules take effect after generated defaults in both the local application and registry consumer. Compare representative computed styles when a browser is available; file presence alone does not establish the CSS cascade.
- Reconcile visual-translation.md with final source and previews. Document important adaptations, omissions, and imagery limitations; preserve the durable mapping in design-notes.md and DESIGN.md before temporary files are removed.
- Search generated application, gallery, example, and registry sources for non-dummy placeholder services and random-photo URLs. Every remote `img`, `Image`, and Avatar image source in downloaded/generated examples and blocks must use `dummyimage.com`; preserve verified user-authored references, imported assets, and licensed assets outside generated example source.
- Check DESIGN.md, tokens.json, CSS, registry, and the confirmed token hash agree. Include actual limitations; source generation is not proof of visual verification.
- Verify DESIGN.md follows assets/DESIGN.template.md with all 13 sections and required rules. ## Choice, presentation, and language checks

- Choice rounds contain exactly two comparable visual specimens and consume only planned high-impact questions. Derived checkpoints contain one specimen and a rationale, without a question.
- The full-page preview contains exactly one integrated design with Desktop and Mobile views. It has no A/B choice or approval popup. Confirmations and revisions arrive in conversation.
- The delivered gallery overview repeats that confirmed integrated design above the component directory. In standalone output, delivery rejects the bundled IntegratedPreview placeholder marker and incorrect overview ordering.
- Check relevant specimen viewports, scrolling, open links, zoom, and readable component sizes. Full device framing is required only for the integrated presentation. No zoom widgets or hints are visible.
- Verify font smoothing in the studio, HTML boards, and React preview documents, including iframe content.
- Send working links and use the available host tool's actual single-select schema. Reject multiple option IDs, stale answers, and premature approvals without mutating state. Cancellation or silence leaves the pending round unchanged.
- Keep review HTML free of feedback inputs and decision buttons. Preserve interactions within component examples.
- Keep skill source text in English. Translate runtime copy, previews, accessible labels, examples, and DESIGN.md into the user's language without changing identifiers.
